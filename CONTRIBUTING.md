# Contributing

Thanks for helping. This guide covers the workflow, code conventions, tests and
the rules that protect users' data and the share-code format. Build
prerequisites and commands are in the [README](README.md); the structure is in
[`docs/architecture.md`](docs/architecture.md).

## Workflow

1. Branch from `main` (`feature/<topic>`, `fix/<topic>`).
2. Make small, coherent commits; each should build and pass the tests.
3. Before opening a pull request run, at minimum:

   ```sh
   cmake --preset core-debug && cmake --build --preset core-debug && ctest --preset core-debug
   scripts/check-format.sh
   ```

   and, if you touched `src/app` or `ui/`, the `debug` preset with Qt
   (`ctest --preset debug` includes the application tests, among them the
   check that QML shows data as plain text) and, after colour changes,
   `python3 ui/dev/check_contrast.py`.
4. Open a pull request against `main`. CI must pass: build and tests on
   Windows (MSVC), Linux (GCC) and macOS (AppleClang) with warnings as
   errors, including the application tests, ASan + UBSan on the Qt-free
   libraries, the format check and the contrast check.
5. Update documentation in the same pull request: the changelog entry under
   *Unreleased*, an ADR for a material trade-off, the support matrix only with
   evidence.

Do not rewrite published history, and do not commit build output, local
databases, logs, downloaded mods, game files or Steam binaries (`.gitignore`
blocks the common ones).

## Commit messages

- Subject: imperative mood, about 72 characters at most, no trailing period
  ("Add Stellaris descriptor parser", "Fix rollback when the backup is missing").
- Body (optional): what and why, wrapped at 72 columns; reference issues.
- Commits are authored by the person submitting them. Do not add
  "generated by" lines or co-author trailers for tools.

## Code conventions

- C++20 on every platform. 4-space indentation, 100 columns, `#pragma once`.
- Types `PascalCase`, functions and variables `camelCase`, members
  `m_camelCase`, constants `kCamelCase`, namespaces `pmm::<module>`.
- Includes use the module path from `src/` (`#include "core/result.hpp"`),
  project headers first; `.clang-format` regroups and sorts them.
- **No Qt below the application layer**: `src/core`, `platform`, `sharing`,
  `persistence`, `games`, `providers`, `services` and `tools/` must build with
  the `core-debug` preset ([ADR 0001](docs/adr/0001-qt-quick-frontend.md)).
  Dependencies point downwards only.
- Expected failures return `pmm::Result<T>` / `Status` with an actionable
  `message` and technical context in `detail`. No exceptions across module
  boundaries.
- Never log or store credentials. Anything exported for diagnostics goes
  through `pmm::redact()`.
- Treat share codes, descriptors, Steam files and helper output as untrusted:
  validate with explicit limits; never build shell commands or URLs from them.
  Start processes only through `platform::startDetached()` (argument vector,
  no shell).
- Short header comments state purpose and invariants; inline comments explain
  non-obvious decisions, not what the code says.
- New libraries are `STATIC` targets `pmm_<module>` with alias
  `PMM::<module>`, configured with `pmm_configure_target()`.

## Formatting and static analysis

- Formatting is defined by `.clang-format`; CI pins clang-format **22.1.8**:

  ```sh
  python -m pip install clang-format==22.1.8   # or LLVM 22 from your package manager
  scripts/format.sh                            # reformat tracked C++ files in place
  scripts/check-format.sh                      # verify without changing anything (CI)
  ```

  Other major versions may format differently; both scripts accept
  `CLANG_FORMAT=/path/to/clang-format`.
- Static analysis: `.clang-tidy` (bugprone, performance, concurrency and
  selected other checks). Run it on a configured build tree:

  ```sh
  scripts/run-clang-tidy.sh build/core-debug                  # all of src/ and tools/
  scripts/run-clang-tidy.sh build/core-debug src/core/model.cpp
  ```

  clang-tidy is not a CI gate yet because existing code still has findings;
  do not add new ones in the files you touch.

- Compiler warnings: `/W4` plus extra warnings on MSVC, `-Wall -Wextra
  -Wpedantic -Wshadow -Wold-style-cast ...` on GCC/Clang
  (`cmake/CompilerWarnings.cmake`). Keep builds warning-free; CI uses
  warnings as errors.
- Sanitizers: `cmake --preset core-sanitize` (Linux/macOS, ASan + UBSan).

## Tests

- Catch2 v3. Each module has `tests/unit/<module>/CMakeLists.txt` registering
  a suite with `pmm_add_test(<name> SOURCES ... LIBS ...)`; CTest labels equal
  the suite name (`ctest --preset core-debug -L pmm_sharing_tests`).
- Tests are hermetic: create unique temporary directories, including paths
  with spaces and non-ASCII characters (for example `Ünïcødé dir/日本語`), and
  never touch real Steam, game or user folders.
- Tests never need proprietary binaries. Workshop helper tests use the fake
  Steam API library built from `tests/unit/providers/fake_steam_api.cpp`.
- Inject time and failures instead of sleeping or relying on the environment
  (see `FileTransactionFaults`, `persistence/testing.hpp`, `Tick` in the
  acquisition reducer).
- Every bug fix comes with a test that fails without the fix.

### Fixtures

- Fixtures live in `tests/fixtures/<module>/` and are read through
  `PMM_FIXTURES_DIR`. They are read-only: copy them to a temporary directory
  before modifying anything.
- `.gitattributes` marks fixtures as binary (`-text`), so they stay byte-exact
  on every platform.
- **Sanitize** anything modelled on real files: placeholder user names and
  paths (`C:/Users/<user>`, `/home/user`), no SteamID64 values, no account
  data, no copyrighted game or mod content beyond the minimal structure needed.
- **Share-code regression fixtures never change.** `tests/fixtures/sharing/v1/`
  is the frozen compatibility contract of protocol version 1: existing `.code`
  and `.json` files must never be edited, regenerated or deleted, even if an
  encoder change makes the golden re-encode test fail (that failure must be
  understood and called out in the changelog, see
  [protocol §7](docs/share-code-protocol.md#7-compatibility-policy)). New
  fixtures are added as new numbered files and cross-checked with an
  independent decoder (`scripts/share-code.py decode`).
- Database fixtures (`tests/fixtures/persistence/v<N>_sample.sql`) are kept
  for every released schema version.

## Protocol, schema and compatibility rules

- The application follows [Semantic Versioning](https://semver.org/). The
  share-code protocol (`PMM1`, `schemaVersion` 1) is versioned independently;
  any change an existing decoder would reject or misread needs a new
  `schemaVersion` or envelope version
  ([ADR 0004](docs/adr/0004-share-code-format.md)).
- Provider keys (`steam-workshop`, `local`) and game keys are part of the
  protocol: never rename them.
- Database migrations are append-only; never edit a released migration
  ([ADR 0008](docs/adr/0008-sqlite-migrations.md)).
- Dependency changes go through `cmake/Dependencies.cmake` (URL + SHA-256), a
  license review in `THIRD_PARTY_NOTICES.md`, and the changelog
  ([ADR 0002](docs/adr/0002-dependencies.md)).

## Real game data

Real installations are for reading only during development. Never write,
rename or delete anything under a Steam folder or `Documents/Paradox
Interactive` from tests or tools, never commit game files, and do not run
Workshop subscribe/download against your account unless you intend to change
your subscriptions. The manual validation procedure
([`docs/validation.md`](docs/validation.md)) is the only place where real game
configuration is changed, deliberately and with a revert step.
